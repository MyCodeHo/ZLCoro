# ZLCoro 性能基准测试

本文档记录 ZLCoro 协程库的性能测试结果和分析。

## 测试环境

- **CPU**: 16 核心（硬件线程）
- **操作系统**: Linux
- **编译器**: GCC 11 with -O2 优化
- **测试日期**: 2026-01-14

## 测试命令

```bash
cd build
cmake -DCMAKE_BUILD_TYPE=Release ..
make benchmarks -j$(nproc)
./benchmarks/coroutine_bench
./benchmarks/scheduler_bench
./benchmarks/io_bench
```

---

## 一、协程性能测试 (coroutine_bench)

### 1.1 协程 vs 线程：创建/销毁开销

| 指标 | 协程 | 线程 | 协程优势 |
|------|------|------|----------|
| 单次创建+执行+销毁 | **14 ns** | 15,454 ns | **1080x 更快** |
| 吞吐量 | 69,904,161 次/秒 | 64,710 次/秒 | **1080x 更高** |

**结论**: 协程创建开销约为线程的 **1/1000**，这是协程最大的优势之一。

### 1.2 协程 vs 预热线程池：纯调度开销（公平对比）

> 注：两者都预热后测试，不包含线程创建开销

| 指标 | 协程调度器 | 预热线程池 | 对比 |
|------|------------|------------|------|
| 单任务耗时 | 941 ns | 492 ns | 线程池快 1.9x |
| 吞吐量 | 1,062,964 /秒 | 2,031,475 /秒 | 线程池快 1.9x |

**分析**: 在公平条件下（都预热），线程池的纯调度效率略高于协程。这是正常的，因为：
- 协程有额外的帧分配、状态机管理开销
- 协程的优势不在纯调度，而在创建成本和并发规模

### 1.3 Generator 生成器性能

| 指标 | 值 |
|------|-----|
| 每次 yield 耗时 | **1.75 ns** |
| yield 吞吐量 | **572,753,432 次/秒** |
| 斐波那契 yield（含计算）| 2.40 ns |

**结论**: Generator 提供了高效的惰性计算能力，接近原生循环性能。

### 1.4 大规模并发能力

| 协程数 | 耗时 | 吞吐量 |
|--------|------|--------|
| 50,000 | 51.79 ms | 965,345 /秒 |
| 100,000 | 104.65 ms | 955,521 /秒 |
| 200,000 | 204.41 ms | **978,432 /秒** |

**结论**: 协程可以轻松支持 **20万+** 并发，吞吐量稳定在 **~100万/秒**。

### 1.5 内存占用对比

| 指标 | 协程 | 线程 | 协程优势 |
|------|------|------|----------|
| 句柄大小 | 8 字节 | 8 字节 | - |
| 运行时内存 | ~256 字节/协程 | 8 MB/线程 | **31,775x 更小** |
| 1000个任务 | 0.25 MB | 7.81 GB | **31,775x 更小** |

### 1.6 协程 vs 普通函数调用

| 指标 | 普通函数 | 协程 | 开销倍数 |
|------|----------|------|----------|
| 调用延迟 | 1.34 ns | 34.68 ns | 25.9x |

**分析**: 协程相比普通函数有 ~26x 的开销，但在 I/O 密集型场景中，I/O 等待时间（毫秒级）远大于协程开销（纳秒级），协程优势明显。

## 二、调度器性能测试 (scheduler_bench)

### 2.1 任务提交性能：协程 vs std::async

| 任务数 | 协程 | std::async | 协程优势 |
|--------|------|------------|----------|
| 100 | 0.95 μs/任务 | 18.01 μs/任务 | **18.9x 更快** |
| 1000 | 1.30 μs/任务 | 18.12 μs/任务 | **13.9x 更快** |
| 5000 | 1.10 μs/任务 | 19.25 μs/任务 | **17.5x 更快** |

**平均**: 协程任务提交比 std::async 快 **16.8 倍**。

### 2.2 任务调度延迟

| 指标 | 协程 | std::async | 协程优势 |
|------|------|------------|----------|
| 平均延迟 | **34 ns** | 10,037 ns | **295x 更低** |
| P50 延迟 | 34 ns | 8,429 ns | 248x 更低 |
| P99 延迟 | **40 ns** | 16,208 ns | **405x 更低** |

**结论**: 协程调度延迟极低且稳定，P99 仅 40ns。

### 2.3 线程池扩展性

| 线程数 | 耗时 | 加速比 | 效率 |
|--------|------|--------|------|
| 1 | 0.44 ms | 1.00x | 100% |
| 2 | 0.26 ms | 1.66x | 83% |
| 4 | 0.14 ms | 3.03x | 76% |
| 8 | 0.09 ms | 4.87x | 61% |

**分析**: Runtime 展示了良好的扩展性，8线程达到 4.87x 加速。效率随线程数增加而下降是正常的（Amdahl 定律）。

### 2.4 工作窃取效率

| 指标 | 值 |
|------|-----|
| 总任务数 | 500 |
| 总执行时间 | 0.75 ms |
| 任务吞吐量 | **667,870 /秒** |

### 2.5 协程链式调用性能

| 链长度 | 单链耗时 | 单环节耗时 | 调用速率 |
|--------|----------|------------|----------|
| 10 | 0.19 μs | 18.82 ns | 53,143 K/s |
| 100 | 1.64 μs | 16.42 ns | 60,909 K/s |
| 1000 | 16.40 μs | **16.40 ns** | **60,958 K/s** |

**结论**: 协程链式调用开销稳定在 ~16ns/环节，每秒可完成 **6000万次** 协程调用。

### 2.6 Runtime 多线程加速（CPU密集型任务）

| 配置 | 耗时 | 吞吐量 | 加速比 |
|------|------|--------|--------|
| 1 线程 | 4.06 ms | 49,244 /秒 | 1.00x |
| 2 线程 | 2.06 ms | 96,952 /秒 | **1.97x** |
| 4 线程 | 1.06 ms | 187,978 /秒 | **3.82x** |
| 8 线程 | 0.77 ms | 261,200 /秒 | **5.30x** |

**结论**: 对于 CPU 密集型任务，Runtime 展示了接近线性的加速比：
- 2线程：1.97x（理想 2x）
- 4线程：3.82x（理想 4x）
- 8线程：5.30x（受限于任务数量和同步开销）

## 三、I/O 性能测试 (io_bench)

### 3.1 Epoll 事件处理性能

| 指标 | 值 |
|------|-----|
| 监听 fd 数量 | 100 |
| 总处理事件数 | 1,000,000 |
| 单事件延迟 | **389 ns** |
| 事件吞吐量 | **2,573,745 /秒** |

### 3.2 TCP 连接性能（系统基线）

| 指标 | 值 |
|------|-----|
| 连接数 | 1000 |
| 单连接建立时间 | **18.34 μs** |
| 连接建立速率 | **54,526 /秒** |

### 3.3 网络吞吐量（系统基线）

| 指标 | 值 |
|------|-----|
| 消息大小 | 1 KB |
| 消息数 | 10,000 |
| 网络吞吐量 | **1,906 MB/s** |
| 消息速率 | **1,952,074 /秒** |

### 3.4 定时器精度

| 目标延迟 | 实际平均 | 误差 | 抖动 |
|----------|----------|------|------|
| 1 ms | 1.05 ms | 5.16% | 71 μs |
| 10 ms | 10.07 ms | 0.71% | 67 μs |
| 50 ms | 50.07 ms | **0.13%** | 63 μs |

**结论**: 定时器精度良好，长延迟误差 < 1%。

### 3.5 Epoll vs Poll

| 方式 | 耗时 | 迭代速率 |
|------|------|----------|
| Epoll | 93.62 ms | 5,341 /秒 |
| Poll | 94.25 ms | 5,305 /秒 |

**分析**: 在 500 fd 规模下，Epoll 和 Poll 性能相当。Epoll 的真正优势在于：
- **O(1) 复杂度**: fd 增加时性能不下降
- **边缘触发**: 减少系统调用次数
- **高并发**: 可支持数万个 fd

## 四、性能总结

### ✅ 协程的核心优势

| 特性 | 数据 |
|------|------|
| 创建速度 | 比线程快 **1000x** |
| 调度延迟 | **34 ns**（P99: 40 ns） |
| 内存占用 | 比线程小 **31,775x** |
| 大规模并发 | 20万+协程，吞吐量稳定 |
| 链式调用 | **16 ns/次**，6000万次/秒 |

### ⚠️ 需要注意的场景

| 场景 | 建议 |
|------|------|
| 纯 CPU 计算（预热后） | 线程池略快 1.5-2x，可接受 |
| 超轻量级任务 | 协程开销可能占比较高 |
| 普通函数调用 | 协程有 ~26x 开销 |

### 🎯 最佳使用场景

1. **I/O 密集型应用**: 网络服务器、数据库客户端、文件处理
2. **高并发场景**: 需要数万甚至数十万并发任务
3. **短生命周期任务**: 频繁创建/销毁的任务
4. **复杂异步流程**: 需要链式调用、组合多个异步操作
